# PHONE-TELEMETRY.md — 手机端埋点设计（下次修订快捷指令时落地）

> 状态: **服务端总入口已就位**（`CONFIG.TELEMETRY` + 信封 `telemetry` 节，2026-07-31）。
> 手机端待做。触发这份设计的实案见 §0。

---

## 0. 为什么要做

2026-07-31 早晨的实案:

```
"DND 定时 20:55" took too long to run.
Shortcut Timed Out
```

**但手机状态全都改对了。** 于是无从判断:

- 是整链超预算，还是某一步特别慢？
- 是网络往返慢，还是 `Set Focus` 的 Wait 累加？
- 状态是超时【之前】改的，还是被杀之后另一次运行补的？

没有分段耗时，这三个问题一个都答不了。

---

## 1. 最关键的一条设计: **记「意图」而不是「结果」**

这是整份设计的核心，也是最容易做错的地方。

| 写法 | 正常运行 | **超时被杀那次** |
|---|---|---|
| 结束时统一写 | ✅ 完整 | ❌ **什么都没有** —— 而这正是你要查的那次 |
| 每步做完写结果 | ✅ 完整 | ⚠️ 缺最后一步，只知道"上一步成功了" |
| **每步动手前写意图** | ✅ 完整 | ⭐ **最后一行就是凶手** |

所以配置默认 `MODE: "intent"`:

```
09:20:31.412  a3f2k1  →GET 网关
09:20:33.180  a3f2k1  →ApplySilent
09:20:33.402  a3f2k1  →ApplyVolume
09:20:33.655  a3f2k1  →ApplyFocus            ← 日志到此为止
                                              ⇒ 死在 ApplyFocus 里
```

「箭头」表示**即将执行**。最后一行没有配对的完成记录 = 它就是被杀的地方。

> 代价: 写入次数翻倍（每步一次而不是每轮一次）。这就是为什么必须有总入口 —— 稳定后关掉。

## 2. 总入口（已就位）

信封里多一节，手机端**先读它再决定记不记**:

```json
"telemetry": {
  "ENABLED": true,
  "MODE": "intent",
  "SLOW_MS": 15000,
  "KEEP_DAYS": 7,
  "run_id": "h2e14zfuz8",
  "server_at": "2026-07-31 08:29"
}
```

| 字段 | 手机端怎么用 |
|---|---|
| `ENABLED` | `false` → 整段跳过，一个字节都不写。**稳定后改这里，不用碰手机** |
| `MODE` | `intent` / `result`，见 §1 |
| `SLOW_MS` | 本轮总耗时超它 → 该轮标 `SLOW`，事后好筛 |
| `KEEP_DAYS` | 本地保留天数，手机端自己清 |
| `run_id` | ⭐ **服务端生成**，本轮所有日志行的分组键 |
| `server_at` | 服务端时刻，和手机时刻一起记 → 能算出钟差 |

### 2.1 ⚠️ 必须有本地默认值

`ENABLED` 来自信封，而信封来自 GET。**GET 失败的那次拿不到配置 —— 而那正是最该记录的一次。**

所以手机端的读法必须是:

```
T1  从信封取 telemetry.ENABLED
T2  If (T1) is empty → 用本地默认（建议 true）
```

不能写成"取不到就不记"，否则网络故障永远查不出来。

### 2.2 `run_id` 为什么由服务端生成

手机端自己 UUID 也能分组，但服务端生成的能**和服务端日志对上同一个 id**。
将来 P-观测回传时带上 `run_id`，一条链路两端的记录就能拼起来 —— 这是免费的，
现在不做也别把口堵死。

## 3. 埋点位置

按「一次运行」的骨架排:

| # | 埋点 | 记什么 | 为什么 |
|---|---|---|---|
| 1 | SyncAll 入口 | `→SyncAll` + 触发因（刺客时刻 / 门铃 / 手动） | 定位是哪种入口慢 |
| 2 | 组 URL 后、发请求前 | `→GET` | **网络是最大变量**，这条和下一条的差值就是往返耗时 |
| 3 | 信封到手 | `←GET` + 字段数 + `server_at` | 有 `server_at` 就能算钟差 |
| 4 | 每个 Apply 之前 | `→ApplyXxx` | §1 的凶手定位靠这条 |
| 5 | 每个 Apply 内部：守卫判定后 | `guard=pass/skip` | 区分"没动手"和"动手失败" |
| 6 | 每个 Apply 内部：动作执行后 | `done` | `Set Focus` 的 Wait 累加在这里现形 |
| 7 | SyncAll 出口 | `←SyncAll` + 总毫秒 + 是否 `SLOW` | 汇总行，正常运行只看这一行就够 |

`Set Focus` 那圈候选名循环建议**每次尝试都记一行**（`try=睡眠`）——
缺 `locales` 降级成全语言时会多试几次，这里能直接量出代价（见 `ACTIONS-APP.md §3.2`）。

## 4. 时间戳精度

原生 `Current Date` 只到**秒**，而单轮预算就 40–80 秒，秒级精度量不出"哪一步慢"。

**用 Actions 的 `Get High-Resolution Timestamp`。**

> 这条推翻了 `ACTIONS-APP.md §4` 把它列为"别用"的判断。当时的理由是"只对延迟实验有意义，
> 而延迟实验没在做"——现在有了超时实案，条件变了。**判断随证据改，不是打脸。**

记录用**相对毫秒**（相对本轮第一条），不是绝对时间:

- 一眼看出步间差值，不用心算
- 行更短，写入更快
- 绝对时间只在第一行记一次

## 5. 写到哪 / 怎么防垃圾

### 5.1 按天分片

文件名 `telemetry-YYYY-MM-DD.txt`。**用文件不用 Note**，理由见 §6.3。好处:

- 天然分片，单个文件不会无限长
- 清理只是删旧文件，不用读改写
- 出问题时你知道去翻哪一天

### 5.2 清理

每天第一次运行时，删掉 `KEEP_DAYS` 之前的文件。挂在**当天第一条日志之后**，
不要挂在入口 —— 清理本身要花时间，别占用最紧张的开头。

### 5.3 关掉之后

`ENABLED: false` 之后不再写入，已有文件不动。你想彻底清就手动删一次。
**不要做"关掉时自动清空"** —— 关掉往往是因为稳定了，而那时的历史数据恰恰有参考价值。

## 6. 埋点成本（**已实测，2026-07-31**）

Ivan 用一个 20 次循环的 benchmark 实测（文件与 Note 各写一次，各夹一对高精度时间戳）:

| | | 预热后中位 | 标准差 | 首次（冷） |
|---|---|---|---|---|
| 前台 | `Append to File` | **36.8 ms** | 2.8 ms | 90.3 ms |
| 前台 | `Append to Note` | 33.9 ms | 2.2 ms | 41.8 ms |
| **后台(锁屏)** | `Append to File` | **36.8 ms** | 2.8 ms | 70.2 ms |
| **后台(锁屏)** | `Append to Note` | 37.4 ms | 3.1 ms | 40.4 ms |

**后台 / 前台 = 1.00× (文件) / 1.10× (Note，在噪声内)** —— 后台不受 I/O 限流影响，
这是本设计最需要确认的一条（触发它的那次 timeout 就发生在后台）。

**结论: 直写，不做缓冲。**

```
12 个埋点 × 37ms ≈ 0.44 秒 ≈ 单轮 30 秒目标的 1.5%
```

为 1.5% 引入"内存缓冲 + 分段落盘"不划算 —— 缓冲会让 §1 的凶手定位变复杂
（被杀时缓冲里的东西全丢），而它要省的东西本来就可以忽略。**初版设计里那条缓冲退路已删除。**

### 6.1 测量方法的已知缺陷（不影响结论）

每个数是 `T1 → 写 → T2` 的差值，**包含一次 `Get High-Resolution Timestamp` 本身的耗时**
（第三方 App Intent，走 IPC，未必便宜）。所以真实写入成本 **≤ 37ms**。

要扣掉它需要加一条基线（连续两次时间戳、中间什么都不做）。**但不必补测** ——
即使把时间戳开销全算在写入头上也才 1.5%，这个缺陷改变不了任何决定。

### 6.2 三条读数解读

1. **冷启动 2.4 倍**（90ms vs 37ms）。benchmark 的 20 次在一次运行内、扩展进程是热的；
   **生产中每轮 SyncAll 都是冷启动**，首次写入按 90ms 算。合计 90+11×37 ≈ 0.5s，仍可忽略。
2. **方差极小**（±2–3ms）→ 这个开销稳定可预测，不会偶发飙高。
3. **文件与 Note 数值相当，但选文件** —— 见 §6.3。

### 6.3 选文件不选 Note 的真正理由

benchmark 里两者只差 3ms（噪声范围内），但有一条**测试没覆盖**的差异:

> `Append to File` 是 **O(1)** 追加；`Append to Note` 很可能是 **O(n)** 的读改写（富文本）。

benchmark 的 note 只有 20 行，生产中会有几百行。**若坚持用 Note，必须按天分片**（§5.1），
否则越写越慢，而且慢的方式是渐进的 —— 等你发现时已经积累了几个月的坏数据。

### 6.4 ✅ 后台已验证（2026-07-31）

benchmark 挂时间自动化、锁屏跑完，**后台与前台几乎一致**（见上表）。
后台冷启动 70ms 反而快于前台的 90ms，说明那个 90 是偶发不是规律。**方案定稿。**

### 6.5 成本拆解（基线实测，2026-07-31）

基线 = 循环体内只放「高精度时间戳 + Set Variable」，中间不做任何事:

| | 中位 | σ | 首次 |
|---|---|---|---|
| 基线（时间戳 + 赋值） | **7.8 ms** | 0.8 ms | 13.5 ms |

拆开之后:

| | 实测 | −基线 | **净写入** | 写入占比 |
|---|---|---|---|---|
| 文件 前台 | 36.8 | 7.8 | **29.0 ms** | 79% |
| Note 前台 | 33.9 | 7.8 | 26.1 ms | 77% |
| 文件 后台 | 36.8 | 7.8 | **29.0 ms** | 79% |
| Note 后台 | 37.4 | 7.8 | 29.6 ms | 79% |

**⚠️ 这推翻了本节初版的推断。** 初版猜「大头是第三方 App Intent 的 IPC」，实际相反:
第三方 App Intent 很便宜（≤7.8ms，还含一次 Set Variable），**写入才是大头（79%）**。

不过原推断有半句仍成立: 四个净写入数几乎相同（29.0 / 26.1 / 29.0 / 29.6），
两种完全不同的存储、两种运行环境成本一致 —— 说明这 29ms 大概率也**不是真正的磁盘 I/O**，
而是动作调度 / 沙盒跨界的固定开销。方向错了，性质判断对了。

### 6.5.1 缓冲的取舍现在有数字了

```
12 埋点   直写         0.44 s
          缓冲成一次写  0.12 s
          差            0.32 s
```

**明知能省 0.32 秒，仍然不缓冲。** 那 0.32 秒买的是「超时那次能定位凶手」——
被杀时缓冲里的东西全丢，而那正是唯一需要日志的场景。
（初版说"缓冲要省的东西可以忽略"，措辞不准；准确说法是: 省得到，但不值得换。）

### 6.5.2 副产品: 纯计时探针

基线 σ 只有 0.8ms，比写入的 ±3ms 还稳 → **高精度时间戳可以放心密集使用**。

于是有两种调试姿势，按场景选:

| 姿势 | 成本/点 | 用于 |
|---|---|---|
| **埋点直写**（本文档主体） | 36.8 ms | 常驻。抗被杀，能定位凶手 |
| **纯计时探针**（只记内存，末尾一次性输出） | 7.8 ms | 临时。怀疑某个指令慢时插十几个，快 4.7 倍 |

### 6.6 不变的一条

`ENABLED: false` 时必须是**零成本** —— 连判断都只做一次，不要在每个埋点处都判一遍。

## 8. 和 P-观测的关系

本设计是**纯本地**的，不回传。P-观测（`FEEDBACK-SELFHEAL.md`）是回传实测态给服务端，
两者互补:

| | 本地埋点 | P-观测回传 |
|---|---|---|
| 答什么 | **为什么慢 / 死在哪** | **做没做成 / 状态对不对** |
| 网络失败时 | 照记（这正是它的价值） | 记不了 |
| 数据量 | 大，本地留几天 | 小，长期留 |

共用 `run_id`，将来能拼成一条完整链路。回传批量端点已经建好（`POST /v2/fact`
的 `{events:[...]}`），要带耗时摘要的话直接塞进 payload 即可，不用再改服务端。
