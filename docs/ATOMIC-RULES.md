## 1. 原子的定义

```
一条规则原子 = (触发因, 条件, 效果)
```

- **触发因** —— 什么把这条规则叫醒
- **条件** —— 叫醒之后，今天算不算数（日型、在场、事件碰撞…）
- **效果** —— 算数的话，哪个字段变成什么、怎么落地

三者独立可换。现状的五旋钮把它们揉在字段配置里，所以任一维度都动不了。

## 2. 效果的三根轴

`once / enforce / on_change` 三个旧名是三根轴的混合投影，这是要根除的牛皮癣。

### 2.1 SHAPE 主张形状（**边界级**）

| | `level` 电平 | `pulse` 脉冲 |
|---|---|---|
| 语义 | 从此刻起持续主张到下一个边界 | 此刻发生一次事件，之后不主张 |
| 同值相邻 | 合并 | **不合并**（今晚的 on 不是昨晚那个 on） |
| 段内被问到 | 回答当前主张 | 回答"无主张" → 该字段不下发 |
| 跨窗口 | 锚定延续 | 不延续 |
| 结束方式 | 需显式终止符 | 自带终止 |

`pulse` = "电平 + 紧随的撤销"的糖。撤销标记（内部 `null`）不出现在配置词汇里，但它在时间线内部删不掉——`pulse` 边界天生承担了它。

#### 2.1.1 真正的旋钮是【主张时长】

`pulse` 与 `level` 不是两种机制，是同一根旋钮的两端：

| 时长 | 形态 | 写法 |
|---|---|---|
| 0 | 脉冲：到点做一次，之后无主张 | `pulse` |
| 有限 | **有界电平**：窗口内持续主张，窗口后无主张 | `level` + `until` |
| 到下一个边界 | 电平 | `level` |

**有界电平是漏发兜底的正解。** 纯 `pulse` 有一个物理黑洞：07:40 那一刻手机在地库/飞行模式/盲窗，
边界就永久错过了——脉冲不跨窗口延续，08:15 心跳进来算出的期望是"无主张"，
于是昨晚的 `sleep|on` 一直挂着。工作日 12:15 的午休边界会把它换掉（最坏窗口 07:40–12:15），
**周末则是 09:30 一路挂到 22:25**，这才是真正难受的那个。

有界电平直接消掉它，不需要任何新机制：

```
07:40 – 08:30   sleep|off   level + always + 守卫 sleep
08:30 之后       无主张
```

08:15 任何一次调用（门铃重试 / 心跳 / 其它入口）进来 → 看到 level 期望 `sleep|off` →
守卫查到当前确实是睡眠 → 解除。窗口之后照样无主张，10 点手动小睡安全。

> **为什么不是"心跳向回追溯 N 分钟内错过的 pulse"**：服务端分不清"漏了"和"守卫故意拦了"。
> 追溯会把被守卫跳过的边界重放一遍，正好把守卫要防的误伤请回来。
> 有界电平不会——守卫在窗口内**每次都重新求值**。

**窗口长度是配置叶子**，默认：

| 边界 | 窗口 | 依据 |
|---|---|---|
| 工作日晨间解除 | 07:40 – **08:30** | 与 `ZONES.MORNING.end` 同源（迟到边界），改一处全跟 |
| 周末晨间解除 | 09:30 – **10:30** | 覆盖离线恢复即可 |
| 夜间进入 | 20:55/22:25 → 晨间解除 | 本来就是电平 |
| 午休两端 | — | `pulse`（Ivan 拍板；午休漏了无关痛痒） |

**长度怎么权衡**：窗口要盖住"离线恢复"这段（门铃在 APNs 侧排队，重连即送达），
但窗口越长，你在窗口内**主动重开**睡眠就越可能被收掉。所以别为了保险无限拉长——
兜底的主力是门铃重试（服务端没收到回传就再按，§7），心跳只是最后一道。

**必须是边界级**，因为 focus 一天之内两种都要用：

```
20:55  sleep|on   level   夜里持续主张
07:40  sleep|off  pulse   交还控制权，白天归人管
```

字段级只能二选一：全 level 则白天误关小睡，全 pulse 则夜间漏了补不回来。

### 2.2 APPLY 执行判据（**边界级**）

| 值 | 判据 | 下发 |
|---|---|---|
| `always` | 收到就做（守卫仍可否决） | `enforce` |
| `if_changed` | 与本地 `la` 比，变了才做 | `on_change` |
| `if_differs` | 与**实测态**比，不一致才做 | 手机端未实现 |

**可观测性不是旋钮，是约束**——决定哪些判据合法：

| 字段 | 读得回来？ | 可选判据 |
|---|---|---|
| focus | ✅ `Get Current Focus` | 三档 |
| media_volume | ✅ 0–1 浮点（台账 §6.2） | 三档 |
| silent | ✅ `Is Silent Mode On`（Actions app，2026-07-29 实测） | 三档 |

> **2026-07-29 更新**: 本节原先有一条硬约束 ——「不可观测字段的记忆只能记住"我做了什么"，
> 永远不知道"你之后改了什么"，搬到云端也解决不了，**除非 iOS 给读接口**」。
> Actions app 的 `Is Silent Mode On` 就是那个"除非"，该约束**作废**。
> 三个字段现在全部可观测 → `if_differs` 对三者都合法 → `la` 的适用面缩到接近零。
>
> ⚠️ 但它的返回值是**本地化**的（中文 `是`/`否`，英文 `Yes`/`No`），
> 必须走和 `current_focus` 同一套 token→本机名解析表，或在手机端先归一成真布尔。
> 详见 `ACTIONS-APP.md` §2.1。

### 2.3 守卫（已实现）

守卫是**策略**，不是缓存优化。**优先级高于一切，包括强制推平**（Ivan 拍板）。判 SKIP → 不动手、不落账，`la` 保持原值，这本身承载信息（§6）。

### 2.4 合法组合

| SHAPE | APPLY | 含义 | 旧名 |
|---|---|---|---|
| pulse | always | 到点必做一次 | `once` |
| pulse | if_differs | 到点了但已是目标态就省一次 | — |
| pulse | if_changed | **不合法**（脉冲没有"上次"） | — |
| level | always | 持续期望态，谁问都推平 | `enforce` |
| level | if_changed | 持续期望态，尊重手动改动 | `on_change` |
| level | if_differs | 真正的 reconcile | — |

## 3. 触发因（全部依据 `CHANNELS.md` 实测）

### 3.1 推/拉分工（台账 §4，本稿沿用不改）

- **拉 = 地基（电平语义）**：已知边界时刻 + 低频心跳。计划内时刻本就是网关算的。
- **推 = 快路径（边沿语义，不可靠）**：计划外变更 → Bark `active` 门铃 → 手机立即拉一轮。推丢了最坏退回现状，等心跳。

### 3.2 入口表

| 触发因 | 手机侧 | 谁发起 | 用于 |
|---|---|---|---|
| `clock@HH:MM` | 时间自动化 ×6 | 手机 | 六个固定边界 |
| `doorbell` | **收到通知**（Bark `active`） | **服务端** | 动态时刻、计划外变更、漂移催同步 |
| `alarm_stopped` | Any Alarm Is Stopped + Label 前缀分流 | 手机 | 起床钩子 |
| `heartbeat` | 低频时间自动化 | 手机 | 地基兜底，永不撤（台账 §4） |

**`doorbell` 是唯一服务端能主动发起的入口**，因此动态时刻、重试、催同步全走它。

> **为什么没有 `focus_changed`**（2026-07-28 删除）：系统自己开睡眠也会触发它 → 多跑一次
> SyncAll → 而单槽忙丢意味着这次多余运行期间别的触发被直接丢掉，等于自制干扰。
> 且它没有落点：服务端不需要在你改专注的瞬间知道——`la` + 守卫已正确处理手动改动，
> 计划外变更由门铃覆盖。**专注变更自动化不用，特定通知内容路由更精准。**

### 3.2.1 触发因是【可见性过滤器】，不是查表的键

这是最容易写错的一处：**不能把规范形式当成"触发因 → 规则"的 K-V 字典去查**。
心跳拿着 `heartbeat` 这个字符串，永远查不到主键写着 `clock@20:55` 的那条规则。

正确的语义是——触发因决定**这次调用能看见哪些边界**：

| 触发因 | 能看见 |
|---|---|
| `clock@HH:MM` / `doorbell` / `alarm_stopped` | 该时刻附近的边界，**含 pulse** |
| `heartbeat` | **只看 level 期望（含有界电平），看不见 pulse** |

这条今天以 `mode=point` / `mode=segment` 的形式隐含存在，但从没写明，
所以它一直是"实现细节"而不是"契约"。**原子化之后必须写明**，否则翻译器很容易被实现成字典。

### 3.3 门铃三条纪律

1. **门铃一律 `active` 档** —— 呈现被 DND 拦、触发照跑（台账 B1）。零打扰是它能用在夜里/清晨的前提；`critical` 只留给必须叫醒人的事。
2. **门铃不是信件** —— 通知内容只做**路由**（选哪条指令），永不作为指令内容。被触发的指令一律带 key 去 GET 拿权威状态。泄露 Bark key 最坏 = 骚扰门铃。
3. **关键词必须带分隔符** —— iOS 通知触发的过滤是 `contains`，而 `contains` 是**子串**匹配（铁则5）：`SYNC` 会命中 `SYNCALL`。**第一条门铃就写 `|SYNCALL|`**，过滤器也写 `|SYNCALL|`，将来加关键词不用回头改所有自动化。

> **触发因标识 ≠ 指令内容。** 起床钩子用 Label 前缀分流、门铃用关键词分流，这些都是
> **路由信息**，不违反纪律2。纪律2 禁的是把"要应用的状态"塞进通知。
> （修订一没写清这点，容易被读成"什么都不能带"。）

### 3.4 触发执行模型的硬约束（台账 §3/§6.4，全部实测）

| 约束 | 实测 | 对本设计的强制要求 |
|---|---|---|
| **单槽·串行·忙丢** | 运行期到达的触发全丢，不排队不补跑；长任务运行期 30 响仅首响生效（B3/B4） | ⭐ 所有边界**必须幂等**；`pulse` 不重放正是这条的自然形状 |
| **回响双发** | 门铃可能撞在同步进行中蒸发 | 关键变更**同一门铃双发，间隔 ≥2 分钟**（> 单轮最坏时长）；门铃幂等，多按无害 |
| **盲窗** | 重启后首次解锁前，通知照送但自动化不落地（E3） | 不做特殊处理，靠解锁后首次心跳幂等补齐 |
| **后台预算** | 锁屏后台 40–80 秒非确定被掐，掐尾部；网络往返 ~1.3s | 单轮 <30 秒；关键动作不置尾 |
| **运行前询问** | 不关则后台完全不触发 | 每条新自动化的上线冒烟必查项 |

## 4. 边界时刻可以是算出来的

### 4.1 出差场景

**既有事实（已在跑，本稿不改）**

1. 日历有 `work_event` 事件，有具体开始时间 08:10
2. `presence` 判定晨间碰撞（`ZONES.MORNING` = 06:00–08:30，Ivan 已把 end 从 08:00 延到 08:30）
3. `wake-alarms` 不注入固定早间组，改建动态闹钟 `GateDyn-Event-0810`

**缺的一环**：`quiet` 晨间解除仍走固定 07:40，于是闹钟 08:10 才响、focus/silent 却 07:40 就解除了。

**方案：门铃**（Ivan 拍板）

```
窗口起点 = 晨间碰撞且事件有具体时间 → 该动态闹钟时间；否则 07:40
窗口终点 = ZONES.MORNING.end (08:30)          ← 与碰撞区同源
效果     = sleep|off  level(有界) + always + 守卫 sleep
触发因   = clock@07:40 ∪ doorbell（服务端在算出的时刻推 active 门铃，双发）
```

窗口终点用 `ZONES.MORNING.end` 不是巧合：碰撞区终点本来就是"再晚就归人管"的那条线，
和 Ivan 说的"超过 08:30 我手动改"是同一句话。改一处全跟。

**为什么是门铃不是起床钩子**：门铃不依赖闹钟标签的命名细节，且与"统一入口"一致。
另见 §4.3 —— 起床钩子在出差日本来就不匹配。

**为什么晚几分钟无害**（Ivan）：真正的需求是**闹钟响之前保持安静**，解除晚几分钟没有影响；
闹钟本身穿静音穿专注（台账 §1 #1/#2），不依赖 focus/silent 先被解除。
门铃走 `active` 档也保证了它不会在闹钟之前把人吵醒。

**边界外归人**：碰撞区终点 08:30 之后不管——Ivan 明确说超过 08:30 手动改。这条原子天然有界。

### 4.2 算不算"字段依赖字段"

不算。晨间解除依赖的是**另一条规则的产出**（`wake-alarms` 的动态闹钟时间），不是另一个字段的值。规则订阅规则是常规操作（`quiet` 就订阅 `presence`）。核心铁律「字段之间不互相依赖」不变。

### 4.3 顺带发现：出差日起床钩子失灵

起床钩子按台账 §3 判 `GateFix-` 前缀分流，但出差日固定早间组**不注入**，响的是 `GateDyn-Event-0810` —— **前缀不匹配，钩子不会触发**。

- 走门铃方案：起床钩子这条不影响本需求，但它自身的这个缺口独立存在，**建议记进台账**
- 若将来要让钩子覆盖出差日：前缀判断扩成 `GateFix-` ∪ `GateDyn-Event-`

### 4.4 白名单

现有 `DND.WHITELIST` 是**时刻**白名单，动态时刻装不进去。原子化后改成**触发因白名单**：

```
clock@{六个时刻} · doorbell · alarm_stopped · heartbeat
```

审计从"边界时刻是否在白名单"改成"边界的触发因是否在白名单"，并可自动派生「手机上要建哪些自动化」——这份清单目前只散在 `PHONE.md` 正文里。

## 5. 书写形式与翻译器

三种写法都要能写，加载期统一翻译成规范形式。**内部只存一种真相。**

### 5.1 规范形式：触发因为主键

```
触发因 → [ { 条件, 字段, 值, shape, apply, 守卫 }, ... ]
```

理由：时刻只是触发因的一种，它是唯一装得下 `doorbell` / `alarm_stopped` 的形状；与白名单、审计、手机自动化清单同构，可自动派生。

### 5.2 书写糖 A：时刻为主键

多字段共用同一批时刻时最省（六个 DND 时刻就是）：

```
20:55  工作日前夜 → focus: sleep|on (level, if_changed, 守卫 none)
                   silent: on      (level, if_changed)
```

### 5.3 书写糖 B：字段为主键

字段有私有时刻时更直观（Ivan 要求补上）：

```
focus:
  20:55 / 22:25       sleep|on   level            if_changed  守卫 none
  07:40 until 08:30   sleep|off  level(有界)      always      守卫 sleep
  doorbell:morning_release
                      sleep|off  level until 08:30  always    守卫 sleep   条件: 晨间碰撞
```

### 5.4 翻译器

**规范形式是源码，时间线是编译产物。** 翻译器的产出不是那张 K-V 路由表，而是每个字段一条
带 shape 与窗口的有序边界序列——也就是今天 `buildFieldTimeline` 已经在产的东西，
查询用 `sampleSegment` 二分。**这套机制现成，不需要新建区间树**：一天 6–10 个边界、
窗口三天，有序数组加二分绰绰有余；上区间树只会多一层没人维护的代码。

- 加载期完成，不在请求路径上
- **可逆检查**：翻完能反向渲染出两种视图，供 `/v2/schema` 与将来的 Pages 前端
- 冲突（两种写法对同一个 (触发因,字段) 各写一份）→ **报错，不静默取一个**
- 编译产物必须保留每个边界的 shape 与窗口终点，否则 §3.2.1 的可见性过滤无从判断

## 6. `la` 的角色（翻案）

之前当成"防轮询的缓存优化"，错了。`la` 记的是**"我上次成功交代的是什么"**，恰好区分了观测分不出的两件事：

| 情形 | 观测到 | `la` | `if_changed` 的结论 |
|---|---|---|---|
| 你半夜手动关掉睡眠 | 无专注 | `sleep\|on` | 期望=la → **不重开** ✅ |
| 20:55 被守卫拦了 | 无专注 | 旧值 | 期望≠la → **补开** ✅ |

**观测知道"现在是什么"，不知道"是谁弄的"；`la` 补的正是后者。**

夜间段定为 `level` + `if_changed`（Ivan 拍板：不重开，本地控制就够）。

### 6.1 推平（手动全量同步）的语义

- 守卫照常生效（优先级高于推平）
- **`pulse` 边界永不重放** —— 脉冲是过去发生过的事件，重放等于凭空再解除一次
- 白天按推平：`silent`/`media_volume` 按期望推平，`focus` 不动（白天本就无主张）

与现在 `?apply=enforce` 行为不同，要改。

## 7. 与自愈的接口

`FEEDBACK-SELFHEAL.md` 的模型是「期望 vs 实测回传」，本就不走 `la`。原子化之后：

- 自愈的催同步就是 `doorbell`，**与刺客走同一条路径**，不需要为自愈单开逻辑
- `if_differs` 判据的输入正是回传的实测态
- 铁律「手机实际态是最终真相」不变；对可观测字段，载体从 `la` 变成实测读数
- 服务端发现漂移 → 推门铃（双发）；仍无回传 → 升级成给人看的通知（`timeSensitive`/`critical`），人点一下闭环

**推论**：自愈上线后非刺客调用变多，`pulse` 的价值随之上升——它保证这些调用不会重放过去的事件。
