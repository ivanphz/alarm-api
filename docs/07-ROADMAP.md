## 1. 下一个大块：回传自愈

**为什么它是当前设计里唯一的缺口**：全 pulse 之后，20:55 那次没跑成就**永远补不上**
（没有后续调用会看见它）。漏发的补救只能靠自愈。

三阶段，每段独立可用：

| 阶段 | 做什么 | 服务端 | 手机端 |
|---|---|---|---|
| **P-观测** | 手机回传实测态，服务端并排期望/实测 | ✅ 批量端点已就绪 | 每个 Apply 尾部加一步回传 |
| **P-建议** | 算 diff，信封多一节 `drift`（只提示不动手） | 1 会话 | 无 |
| **P-自愈** | 服务端发现漂移 → 推门铃补一次 | 1 会话 | 新指令 ApplyDrift |

完整设计见 [10-SELFHEAL](10-SELFHEAL.md)。**先做 P-观测**。做完才能上 `if_differs` 判据（比实测态而不是比本地 `la`）。

回传形状见 [03-CONTRACT](03-CONTRACT.md) §5。三个字段现在**全部读得回来**
（`silent` 靠 Actions 的 `Is Silent Mode On`），所以观测是完整的。

## 2. 多设备（Ivan 2026-07-31 提出）

**目标**：所有设备状态同步，但**只有一台响闹钟**。

已有基础：`?device=` 参数、per-device 的 profile 与 `la`。

要做的：

| # | 事项 | 说明 |
|---|---|---|
| 1 | 区分**共享字段**与**独占字段** | `focus`/`silent`/`volume` 共享；`alarms` 只发给主力机 |
| 2 | 多目标推送 | 见 [06-OPERATIONS](06-OPERATIONS.md) §0.1 的 `PUSH_TARGETS` |
| 3 | 安卓支持 | Bark 是 iOS 专属；安卓走 ntfy，driver 层已为此留口 |

### 2.0 平台差异分三类，别用一层解决全部

| 类型 | 例子 | 归属 | 加新平台的成本 |
|---|---|---|---|
| **① 标识符差异** | 地图 App：iOS `com.apple.Maps` / 安卓 `com.google...`；勿扰的中英文名 | **token + `resolve` 表** | 云端加一张表 ✅ 已实现 |
| **② 能力差异** | 安卓无 iOS Focus 模型；安卓有媒体/铃声/闹钟/通知四路音量 | **设备能力声明**（只留形状，未实现） | 加一节配置 |
| **③ 执行机制差异** | iOS 快捷指令 / 安卓 Tasker | **执行器自己的事，契约不知道** | 写一个新执行器 |

**判据**：问「这个差异能不能用一张对照表翻译掉？」能 → ①；不能但能声明有无 → ②；
连声明都不必、纯粹是「怎么动手」→ ③。

能力声明的预留形状：

```js
PLATFORMS: {
  ios:     { fields: ["focus", "silent", "media_volume"] },
  android: { fields: ["silent", "volume_media", "volume_ring"] },
}
```

服务端据此**只下发该平台支持的字段**。**安卓碎片化在这层吸收** ——
每台能力不同就各自一个 profile，不强求一致。
另：`?platform=` 由设备**自报**，服务端不维护注册表，新设备接入零配置。

### 2.1 「一台开了专注，其他都跟着开」

Ivan 的设想。**依赖 P-观测**，路径是：

```
设备A 手动开专注 → 回传 applied_focus → 服务端记为事实
   → 设备B 下次调用（或被门铃叫醒）→ 看到该事实 → 跟着开
```

**好消息：机制已经就位，不需要新造。**（来自原 HORIZON §3 的判断）

| 已铺的路 | 状态 |
|---|---|
| `?device=` 参数三阶段全程带 | ✅ |
| KV 命名空间 `fact:<device>:*` | ✅ |
| config 深合并支持 `PROFILES.<device>` 分层 | ✅ |
| 插件 `scope: per-device \| shared` 已声明 | ✅ |
| 闹钟标签天然按设备隔离 | ✅ |

> **跨设备联动（A 写 shared 事实 → B 订阅）已被 facts + scope 机制覆盖，无需新机制。**
> 加一台设备 ≈ 加一节配置 + 手机跑一遍装配，**零代码**。

**纪律**：任何新端点从第一天带 `?device=`；任何 KV 键带 `<device>` 段。

要注意的坑（现在别做，做的时候回来看）：

- **回环**：B 跟着开之后也会回传，不能让它再触发 A
- **时序**：谁的状态是权威？建议「最后一次人工操作」优先，机器执行的不算
- **一致性**：设备离线期间的状态漂移怎么收敛

## 4. 服务器精度（低优先，Docker 方案）

`server/` 目录里有完整实现（调度器 + Dockerfile + compose + GitHub Actions 构建）。
**现阶段不需要** —— cron 调成每分钟就够（延迟 ≤60 秒，占免费额度 1.4%）。

将来真正值得捡起来的两个理由（Ivan 2026-07-31 提出）：

1. **ICS 变更检测** —— 服务器每 30 秒拉 ICS 只算哈希（不解析语义，规则仍只在 Worker），
   变了才去取新计划。日历改动的生效延迟从分钟级降到 30 秒。
2. **分布式轮询防封** —— 高频拉 ICS 可能被源站限流；10 台机器各隔 10 分钟拉一次，
   等效 1 分钟粒度而单 IP 只有 1/10 频率。

> 更优雅的形态：**Worker 干脆不开 cron**，由服务器检测到 ICS 变化后直接推 Bark。
> Worker 回到纯被动，主动性完全在服务器。等真要做时按这个方向。

## 5.1 想加但还没加的小检查

| 检查 | 抓什么 | 为什么值得 |
|---|---|---|
| **规则空匹配探测** | 某条规则在 ±400 天里一次都不命中 → 多半是轴值拼错 | 连拼写错误一起抓，静态分析做不到（[02-RULES](02-RULES.md) §6.1） |
| **格式嗅探** `sniffFormat()` | 外部源不必声明 `type`：能 `JSON.parse` → json；含 `BEGIN:VCALENDAR` → ics | 做 todo 通道时一并做最省，一个函数全线复用 |
| **原子重命名** | `workday`/`rest` → `work_scheduled`/`resting` | 现名看着互斥实际不是，照字面写规则必错（[01-CONCEPTS](01-CONCEPTS.md) §4.1）。**改名成本随时间指数上升** |
| **轴值校验** | `when` 里的值不在该轴的合法枚举内 → error | 现在只校验轴**名**，值写错（`morning:["wrok"]`）会静默永不命中 |
| **死配置检测** | 某条规则从未被任何日型命中 → warn | 与空匹配探测同源 |
| **`/v2/schema` 补 `atoms` 段** | 下发每根轴的类型/标签/合法值 | GUI 的下拉直接渲染它；**加一根轴 → 端点自动多一项 → 前端零改动**。这是检验「原子自声明」成不成立的判据 |

两者共同的纪律：**嗅探/探测失败绝不猜、绝不静默，报响亮错误。**

## 5.2 日型层还缺的表达力（原 RULE-TABLE 设计，未实现）

现在的 `when` 只能断言四根轴的**枚举值**。原设计稿里还有两样值得将来补：

**① 负索引** —— 段内第几天，负数从末尾数：

| 想表达 | 谓词 |
|---|---|
| 节后第一个工作日 | `work_streak_index: 1` |
| **长假后**第一个工作日（区别于普通周末后） | `work_streak_index: 1, prev: { rest_block_length: {gte:3} }` |
| 长假最后一天 | `resting: true, rest_block_index: -1` |
| 节前最后一个工作日 | `work_streak_index: -1` |

> ⚠️ **负索引的正确性依赖「整个块可见」**。`restdays` 现在扫 ±16 天；
> 若某个块延伸到扫描窗口之外，**必须报 warn 并按无主张处理，绝不给一个错的数**。

**② 数值算子** —— `gte` / `lte` / `gt` / `lt` / `in` / `not_in` / `not`。
算子集合与 guards 保持同一套心智，但**不共用实现**（guards 在手机端求值、日型在服务端），
两边各自封闭校验，未知算子响亮报错。

**③ `values_from` 值域声明** —— 让 schema 声明「值域来自配置路径」，
如 `school_break: { values_from: "SCHOOL_BREAK.RANGES[].key" }`。
这样你在 config 里加一个 `spring`，将来 GUI 的下拉自动多一项，前端零改动。
